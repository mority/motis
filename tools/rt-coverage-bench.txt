================================================================================
 A/B BENCHMARK: nigiri "drop rt_timetable if not needed" (rt-coverage branch)
================================================================================

WHAT THIS MEASURES
------------------
nigiri branch `rt-coverage` adds a check in `raptor_search_with_dir()` that
drops the `rt_timetable` pointer when the real-time coverage interval cannot
overlap the query's reachable time window. When it fires, the search falls into
the existing `Rt = false` raptor instantiation and skips all real-time lookups.

Two scenarios, each run with nigiri master and with nigiri rt-coverage:

  A  queries on the same date the random delays are generated for
     -> the check must NOT fire; results and search counters must be identical
        to master. This is the regression check.

  B  same origin/destination pairs, queries a month after the delay date
     -> the check MUST fire; results must still be identical to master, and
        the search work should drop sharply.

Expected outcome: `motis compare` reports "equal" for every query in both
scenarios. In A every search counter matches master exactly. In B the counters
drop (with a 10-query pilot on Germany: n_routes_visited 9.3x lower,
execute_time 4.5x lower).


--------------------------------------------------------------------------------
0. PREREQUISITES
--------------------------------------------------------------------------------
- An imported motis data directory (`motis import`), i.e. a directory with
  `config.yml`, `tt.bin`, ... The pilot used a Germany GTFS import with
  timetable.first_day = 2026-08-20, num_days = 365.
- SSH access to github.com (the `.pkg` nigiri url is an SSH url).
- ~2 GB free disk for the response files (4 x ~400 MB at 1000 queries).
- Roughly 16 CPU threads; the pilot machine had 16.

Set these once:

  export MOTIS=$HOME/code/motis                 # motis checkout
  export DATA=$MOTIS/cmake-build-release-gcc-13/data   # imported data dir
  export BUILD=$MOTIS/cmake-build-release-gcc-13       # cmake build dir
  export WORK=$HOME/rt-coverage-bench           # scratch dir for this benchmark
  mkdir -p "$WORK"


--------------------------------------------------------------------------------
1. WHY THE MOTIS BASE IS NOT HEAD  (read this before "fixing" the build)
--------------------------------------------------------------------------------
motis cannot be built against nigiri master at any commit that carries the
random-delay tooling. `src/endpoints/routing.cc` uses `query::rt_mode_both_`
and the 6-argument scheduled-slot `raptor_search`, and `exe/generate.cc` uses
`n::routing::rt_mode::off` -- all of which exist only on the nigiri `rt-raptor`
branch, not on master and not on rt-coverage. This is true of motis HEAD and of
the whole rt-raptor line, including b02982a, which pins nigiri master in `.pkg`
but does not actually compile against it.

So the benchmark base is:

    motis ed0360f  ("fix one-to-many off-by-one crash", newest ancestor with
                    zero rt-raptor API use, pins nigiri master)
  + the six random-delay files taken verbatim from motis c473955
    (none of them reference rt_mode, so this is the same tooling as on HEAD)

If you would rather benchmark on motis HEAD, the alternative is to rebase the
two nigiri coverage commits onto nigiri `rt-raptor` and compare
rt-raptor vs rt-raptor+coverage instead. That changes the baseline.

--------------------------------------------------------------------------------
4. PICK THE DATES
--------------------------------------------------------------------------------
  export DELAY_DATE=2026-09-01     # queries in scenario A, and the rt feed day
  export FAR_DATE=2026-10-01       # queries in scenario B

Constraints:
- Both must be inside the timetable's date range (see `timetable.first_day` /
  `num_days` in $DATA/config.yml).
- `--random_delays` generates data for DELAY_DATE *and the following day*, so
  coverage spans [DELAY_DATE, DELAY_DATE+2d).
- For scenario B the check only fires if the query's reachable window misses
  that. The window is [FAR_DATE-2d, FAR_DATE+2d+max_travel_time], and
  max_travel_time defaults to 5 days -- so FAR_DATE must be at least ~4 days
  after DELAY_DATE+2d. A month apart is comfortable.


--------------------------------------------------------------------------------
5. GENERATE THE QUERIES  (do this ONCE -- both variants must see the same file)
--------------------------------------------------------------------------------
`motis generate` always writes `queries.txt` into the *current* directory.
`--lb_rank false` is the "uniformly at random" origin/destination mode.
Scenario B is derived from A by rewriting only the date, so the OD pairs are
identical and the date is the only variable.

  cd "$WORK"
  "$WORK/motis-nigiri-master" generate \
      -d "$DATA" \
      -n 1000 \
      --first_day "$DELAY_DATE" \
      --last_day  "$(date -u -d "$DELAY_DATE + 1 day" +%F)" \
      --lb_rank false

  # force the RAPTOR algorithm (default is PONG, which does not go through
  # raptor_search_with_dir where the check lives)
  "$WORK/motis-nigiri-master" params -p "?algorithm=RAPTOR" \
      -i queries.txt -o queries_A.txt

  sed "s/time=${DELAY_DATE}T/time=${FAR_DATE}T/" queries_A.txt > queries_B.txt

Verify:

  wc -l queries_A.txt queries_B.txt                       # 1000 each
  grep -o 'time=[0-9-]*' queries_A.txt | sort -u          # only $DELAY_DATE
  grep -o 'time=[0-9-]*' queries_B.txt | sort -u          # only $FAR_DATE
  grep -c 'algorithm=RAPTOR' queries_A.txt                # 1000
  diff <(sed 's/&time=[^&]*//' queries_A.txt) \
       <(sed 's/&time=[^&]*//' queries_B.txt) && echo "OD pairs identical"

NOTE: `motis generate` uses a global atomic counter as its RNG seed and runs
multi-threaded, so two generate runs are not guaranteed to produce the same
queries. That is why the set is generated once and reused for all four runs.

`--last_day` is set to DELAY_DATE+1 on purpose: generate does
`last_day = max(first_day + 1d, last_day)` and then picks a random day in
[first_day, last_day), so every query lands on DELAY_DATE. The time of day is
random in [06:00, 18:00).


--------------------------------------------------------------------------------
6. RUN THE FOUR BATCHES
--------------------------------------------------------------------------------
Note that `--rd_date` is $DELAY_DATE in ALL four runs -- the real-time feed is
the same in every run; only the query date changes between A and B.

  cd "$WORK"
  for scen in A B; do
    for v in master rt-coverage; do
      echo "=== $scen / $v ==="
      "$WORK/motis-nigiri-$v" batch \
          -d "$DATA" \
          -q "queries_$scen.txt" \
          -r "resp_${scen}_${v}.txt" \
          --random_delays --rd_date "$DELAY_DATE" \
          > "batch_${scen}_${v}.log" 2>&1
      echo "exit=$?"
    done
  done

Each run loads the full dataset first (~1-2 min) and then runs the queries on
all hardware threads. Rough pilot-scaled estimate for 1000 queries on Germany
with 16 threads: A ~8 min per variant, B ~11 min (master) and ~3 min
(rt-coverage). Total well under an hour.

Confirm the feed is what you expect -- every log should contain a line like:

  random delays: seed=0, date=2026-09-01, days=[2026-09-01, 2026-09-03),
  1490389 covered (297086 of them delayed), 0 cancelled transports

Add `--n_threads 1` to `batch` if you want less noisy per-query timings (much slower).

7. COMPARE
--------------------------------------------------------------------------------
7a. Itinerary equality -- this is the correctness result.

  cd "$WORK"
  "$WORK/motis-nigiri-rt-coverage" compare \
      -q queries_A.txt -r resp_A_master.txt resp_A_rt-coverage.txt
  "$WORK/motis-nigiri-rt-coverage" compare \
      -q queries_B.txt -r resp_B_master.txt resp_B_rt-coverage.txt

Both must print "consumed: 1000 / equal: 1000".

The response files are NOT byte-identical even when every itinerary matches --
the `debugOutput` object carries the timing/counter differences. That is
expected and is exactly what 7b reads.

7b. Search-work counters.

  python3 - <<'PY'
import json, os
work = os.environ["WORK"]
def load(p):
    with open(os.path.join(work, p)) as f:
        return [json.loads(l) for l in f]
metrics = ["execute_time", "n_routes_visited", "n_earliest_trip_calls",
           "n_footpaths_visited", "lb_time"]
for scen, title in [("A", "A: queries on the delay date (check must NOT fire)"),
                    ("B", "B: queries a month later (check MUST fire)")]:
    A = load(f"resp_{scen}_master.txt")
    B = load(f"resp_{scen}_rt-coverage.txt")
    print(f"\n{title}")
    print(f"  {'metric':26} {'master':>16} {'rt-coverage':>16} {'ratio':>8}")
    for m in metrics:
        sa = sum(r.get("debugOutput", {}).get(m, 0) for r in A)
        sb = sum(r.get("debugOutput", {}).get(m, 0) for r in B)
        r = (sa / sb) if sb else float("nan")
        print(f"  {m:26} {sa:>16,} {sb:>16,} {r:>7.2f}x")
    same = sum(1 for x, y in zip(A, B)
               if x.get("itineraries") == y.get("itineraries"))
    ia = sum(len(r.get("itineraries", [])) for r in A)
    ib = sum(len(r.get("itineraries", [])) for r in B)
    print(f"  itineraries: master={ia}, rt-coverage={ib}; "
          f"identical: {same}/{len(A)}")
PY

  # wall-clock summary per run
  grep -H -E "Processed .* queries|      average:" batch_*.log

8. HOW TO READ THE RESULT
--------------------------------------------------------------------------------
PASS looks like:

  Scenario A: every counter ratio is 1.00x (bit-for-bit identical search work)
              and compare says 1000/1000 equal.
              -> the check correctly kept the rt_timetable everywhere.

  Scenario B: compare says 1000/1000 equal, and n_routes_visited /
              execute_time drop substantially.
              -> the check fired and the results did not change.

FAIL modes to watch for:

  - A shows differing counters or unequal itineraries
      => the check dropped the rtt when real-time data was relevant. Bug in
         `needs_rt()` (window too narrow, or coverage_ not tracking something).
  - B shows no counter drop
      => the check never fired. Check that FAR_DATE is far enough (section 4)
         and that queries really carry algorithm=RAPTOR.
  - B shows unequal itineraries
      => dropping the rtt changed results even though coverage was disjoint;
         something outside `coverage_` influences the search (e.g. td footpaths
         -- those are only guarded by `prf_idx_ == 0`).

--------------------------------------------------------------------------------
9. CAVEATS
--------------------------------------------------------------------------------
- `--rd_coverage` defaults to 1.0, i.e. an rt_transport is materialised for
  essentially the whole day's service. The B speedup scales with how much
  real-time data the feed actually carries; a sparser feed shrinks it.
- Scenario A is the scenario originally asked for, but it never exercises the
  drop -- it only proves the branch does not regress the normal path. B is what
  demonstrates the feature.
- These are forward (departure-time) queries. `arriveBy=true` widens the
  relevant window in the other direction; if you want that covered, add a third
  query set with `params -p "?arriveBy=true"` and move FAR_DATE *before*
  DELAY_DATE instead.
- 1000 queries makes the counter ratios solid; wall-clock timings are still
  affected by machine load since all runs share the box sequentially.

================================================================================
11. PONG VARIANT  (nigiri eda0261a "pong: drop rtt ptr if not needed")
================================================================================

WHAT IS DIFFERENT
-----------------
The same drop now also happens for PONG. The check sits in
`pong_search_with_dir()` (src/routing/raptor/pong.cc), i.e. before the Vias/Rt
dispatch, and uses `pong_needs_rt()` instead of `needs_rt()` because PONG's
reachable window is not the same as range RAPTOR's:

  - range RAPTOR extends its interval through `interval_estimator::extension()`,
    which clamps to +-2 days (`data_type_max_interval_`), the external interval
    and `q.max_interval_`. `max_interval()` is that hard ceiling.
  - PONG has no such ceiling: it walks the start time one found journey at a
    time and stops when it has enough connections or a ping comes up empty.
    Nothing bounds that statically, so the window has to be the whole external
    interval of the timetable in search direction.
  - PONG also looks `kMinLookAhead` (1 day) further than `max_travel_time_`
    (`worst_time_at_dest` in `pong()`), so the window is widened by that too.

For forward queries this makes no practical difference to scenario B: the
window starts at the query time, so coverage that lies entirely before the
query is still disjoint and the rtt is still dropped.

HOW THIS RUN WAS DONE
---------------------
Sections 0-6 apply unchanged, with these deltas:

  - binaries: `motis-nigiri-master` (nigiri a614f550, reused from the RAPTOR
    run) vs `motis-nigiri-pong-coverage` (nigiri eda0261a).
  - queries: derived from the SAME `queries.txt` as the RAPTOR run, so the OD
    pairs and times are identical and `algorithm` is the only difference:

      ./motis-nigiri-master params -p "?algorithm=PONG" \
          -i queries.txt -o queries_A_pong.txt
      sed "s/time=${DELAY_DATE}T/time=${FAR_DATE}T/" \
          queries_A_pong.txt > queries_B_pong.txt

    PONG is the API default, but setting it explicitly documents the intent.
    PONG only actually runs when `pong_applicable` holds
    (src/endpoints/routing.cc): `timetableView` (default true) and
    `arriveBy != extend_interval_later`. For these forward queries that is
    satisfied. Verify per response with `debugOutput.algorithm == 1` (0=RAPTOR,
    1=PONG, 2=TB) and check no log contains "PONG EXCEPTION" (that is the
    silent fallback to RAPTOR).
  - driver: `tools/rt-coverage-bench-run-pong.sh`, analysis:
    `tools/rt-coverage-bench-analyze-pong.py` (both expect $WORK to hold the
    binaries and query files; the analysis script reads $WORK too).
  - 1000 queries, Germany, `--n_threads 8`.

KNOWN GAP (measured in section 12)
----------------------------------
`arriveBy=true` (backward) queries. PONG's backward window reaches from the
query time back to the START of the timetable, so a backward query placed AFTER
the coverage keeps the rtt, where range RAPTOR (capped at -2 days -
max_travel_time) would drop it. A backward query placed BEFORE the coverage
still drops it. Section 12 measures exactly this.

Closing the gap is not a `needs_rt()` change -- it needs PONG's walk to get a
static ceiling (e.g. honour
`q.max_interval_` / `interval_estimator::max_interval()`), after which
`pong_needs_rt()` could use the same window as `needs_rt()`.


================================================================================
12. arriveBy=true  (backward queries), RAPTOR *and* PONG
================================================================================

WHY THIS IS A SEPARATE RUN
--------------------------
Sections 6-11 are forward queries. Backward queries widen the relevant window
in the other direction, and that is where the two algorithms differ most:

  range RAPTOR   window = [t - 2d - max_travel_time, t + 2d]  (capped)
  PONG           window = [timetable start - max_travel_time - kMinLookAhead, t]

So a backward query placed AFTER the coverage is disjoint from it for RAPTOR
but not for PONG -- PONG's walk has no static ceiling, so its window has to
reach back to the start of the timetable.

Three query dates against the coverage [2026-09-01, 2026-09-03):

  C  2026-09-01  on the delay date     no check may fire (regression check)
  D  2026-08-15  before the coverage   both checks must fire
  E  2026-10-01  after the coverage    RAPTOR fires, PONG cannot

Query sets are derived from the same `queries.txt` as every other section, so
the OD pairs are identical throughout:

  for alg in RAPTOR PONG; do
    lc=$(echo $alg | tr A-Z a-z)
    ./motis-nigiri-master params -p "?arriveBy=true&algorithm=$alg" \
        -i queries.txt -o queries_C_${lc}.txt
    sed "s/time=2026-09-01T/time=2026-08-15T/" \
        queries_C_${lc}.txt > queries_D_${lc}.txt
    sed "s/time=2026-09-01T/time=2026-10-01T/" \
        queries_C_${lc}.txt > queries_E_${lc}.txt
  done

Driver: `tools/rt-coverage-bench-run-arriveby.sh`.

HOW TO READ THIS
----------------
C is the backward regression check and passes for both: every counter is
bit-for-bit identical, so neither check fires while the real-time data is
relevant. That is the important one -- backward is where the window math
differs (the `- max_reach` branch in `needs_rt()`).

D shows the backward drop works for both algorithms, with the same ~9x / ~8x
`n_routes_visited` collapse the forward runs showed.

E is the cost of PONG's missing ceiling, in numbers: identical OD pairs, an
identical coverage interval, and RAPTOR gets 9.21x while PONG gets 1.00x. In
practice this is the common shape -- real-time coverage sits around "now" and
